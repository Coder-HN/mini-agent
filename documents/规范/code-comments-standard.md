# 项目代码注释规范

本文约定本仓库内 **Go / PHP / Python / TypeScript·JavaScript / SQL / Shell** 等代码的注释风格与粒度，目标是：**后来者能快读、少猜、敢改**，而不是为注释而注释。

---

## 1. 总原则

1. **解释「为什么」和边界，不翻译「做什么」**  
   若代码本身已自解释（清晰的命名、小而单一的函数），不必逐行复述。

2. **对外（导出/公共 API）先于内部**  
   导出符号、HTTP/RPC 接口、配置项、数据库迁移的意图，优先写清楚；私有实现可在复杂处补注释。

3. **与业务强相关的约束必须落笔**  
   例如：权限模型、幂等假设、与旧版兼容开关、限流/计费、`empty` 与 `0` 在 PHP 中的陷阱、微信/CRM 侧字段语义等。

4. **语言一致**  
   本仓库现有代码中 **中文注释与说明占主导**（如 Go 的 `goldscript` 包）。**同一文件内**保持一种主语言，避免中英一句一换。专有名词（`idempotency-key`、SDK 名）可保留英文。

5. **注释随代码改**  
   行为变更时同步更新注释；删代码时删无效注释。误导性注释比没注释更差。

6. **避免过度封装**  
   结构应服务于可读与可改，而不是为「整洁」或「可复用」提前拆层。仅一处使用的两三行逻辑 **inline 即可**，不必单独抽函数/类/Hook/Helper；已有成熟抽象时直接复用，**禁止**再套无增益的 wrapper、Facade、Manager 中间层。过度封装会迫使读者反复跳转，反而要靠注释补上下文——优先写平铺、命名清晰的代码，减少「解释封装本身」的注释负担。

---

## 2. 建议必须写注释的场景

| 场景 | 说明 |
|------|------|
| 包/模块职责 | 一句话说明边界：负责什么、不负责什么、主要入口在哪一文件 |
| 导出类型与导出函数（Go/TS） | 行为、返回值误差、错误或 `nil`/空值的含义 |
| 模块与公开 API（Python） | 模块 docstring 说明职责；公开类/函数 docstring 写清参数、返回值与异常 |
| 公共类与 public 方法（PHP） | 用途、关键参数、失败时的表现 |
| 非显而易见的算法或公式 | 来源、时间/空间假设、与论文/需求文档的对应关系 |
| 安全与合规 | 鉴权、敏感数据处理、为何不能记录明文密钥等 |
| 与时序/并发相关 | goroutine 生命周期、锁顺序、与 PHP 会话/缓存的一致性假设 |
| 魔法数字与枚举 | 为何是这些取值、与协议或表结构的映射 |
| 兼容与开关 | `mode`、`sample_kind`、feature flag 对行为的分支 |
| SQL 迁移 | 适用环境、执行顺序依赖、回滚注意事项（若适用） |

---

## 3. 应避免的反模式

- **复述代码**：`// i 自增` 这类无信息增量。
- **过时注释**：逻辑已改，注释仍写旧行为。
- **大块被注释掉的死代码**：应删除，需要时从版本控制找回。
- **泄漏秘密**：在注释中写真实密钥、内网未公开 URL（可用占位说明「见配置/秘仓」）。
- **无编号的多段 TODO**：应写清责任人或工单/日期，或使用统一前缀（见下文）。
- **过度封装**：为单行或两三行、且仅一处调用的逻辑单独建函数/类/Hook/Util，读者需多次跳转才能跟上主流程。
- **无增益的抽象层**：在已有 Service/Repository/Provider 外再套 Facade、Manager、Handler，却不改变边界、测试方式或错误语义。
- **为假想复用提前抽象**：当前只有一条路径，却引入策略模式、插件体系或大量配置驱动分支；应等第二处真实复用再抽。

## 4. 分语言约定

### 4.1 Go

- **每个可编译包**：文件顶部或 `doc.go` 用一段 **package comment**（与 `package xxx` 紧邻），说明包职责与主要调用方。
- **所有导出符号**（`type`/`func`/`const`/`var`）：使用 **Go doc 风格** —— 注释以符号名开头一句摘要，必要时空行后接段落说明参数、错误、并发安全。
- **结构体字段**：对 JSON/API 协议字段、可选字段语义、单位（秒/毫秒）写简短行内或段落注释。
- **复杂分支 / `go` / `defer`**：在分支或 goroutine 启动处说明 **为何** 这样写、取消与超时策略。

参考现有风格：`go/internal/goldscript/service.go`（包说明、导出方法、`AnalyzeRequest` 字段注释）。

### 4.2 PHP（ThinkPHP 等）

- **类**：类上方用 docblock 说明职责、继承关系、重要 Trait。
- **public / protected 方法**：`/** ... */` 写清用途、`@param`、`@return`；若副作用（写 session、die、输出 JSON）需写明。
- **`_initialize`、路由分发、RBAC 例外**：说明安全假设（如「ajax opt 禁用 public」），与现有 `PublicAction` 中注释风格对齐。
- **长 SQL 或链式 `where`**：在拼装原因复杂时，用简短中文说明筛选意图或历史包袱。

### 4.3 Python

- **模块与包**：文件顶部用 **module docstring**（`"""..."""`）说明职责、主要依赖与调用方；`__init__.py` 可一句话概括包边界。
- **公开类、函数、方法**（无 leading `_` 或刻意对外暴露的符号）：用 **docstring** 写清用途、参数、返回值与可能抛出的异常；复杂逻辑可分段，不必逐行复述。
- **Pydantic / dataclass 字段**：协议字段、单位（秒/毫秒）、与 Go/PHP 侧字段映射等非自明语义，用 `Field(description=...)` 或行内注释说明。
- **魔法数字、批大小、超时、feature flag**：在常量定义处用 `#` 注释 **为何** 取该值（可与 Go 侧常量对齐时注明对应包/文件）。
- **并发与 I/O**：线程锁顺序、LRU/连接池生命周期、与外部 API 限流假设等，在启动或封装处简短说明。

参考本仓现有风格：`apps/min_agent/tools/query.py`、`packages/agent_core/` 下模块 docstring 与公开函数注释。

### 4.4 TypeScript / JavaScript（含 React）

- **对外导出的函数、组件、hooks**：用 **JSDoc 或 TSDoc**（`/** ... */`）说明参数、返回值、副作用；复杂 `useEffect` 写清依赖含义与清理逻辑。
- **与后端契约**：构建 URL、识别 `error` 码、轮询间隔等，若协议非自明，注释中写明对应后台路由或文档链接（`documents/` 内路径即可）。
- **`'use client'` / Server vs Client**：若在边界处容易误用，一行说明数据从哪来。

### 4.5 SQL（迁移脚本）

- 文件头部注释：**目的**、是否可重复执行、是否依赖某次先发版、**禁止**在无说明的情况下在生产手工改序号。
- 大段 DDL 可对「为何加该索引/字段」各一行说明。

### 4.6 Shell

- 脚本开头：`set -euo pipefail` 等选项、入参、依赖的外部命令。
- 危险操作（删库、递归 rm、`git push --force`）：必须注释 **作用域与回滚思路**。

---

## 5. TODO / FIXME / HACK

- 统一前缀：`TODO(username或工单): 说明` 或 `TODO(2026-04): 说明`。
- `FIXME`：已知错误路径或临时方案，需后续修复。
- `HACK`：不得已的 workaround，需写 **原因** 与 **理想修复方向**。

避免无上下文的孤立 `TODO`。

## 6. 提交前自检（面向作者）

- [ ] 新增的导出 API / 公共方法是否有的一句话说明？
- [ ] 是否把业务约束（权限、兼容、限流）写在了读者会看的地方？
- [ ] 是否删除或更新了因本次修改而过时的注释？
- [ ] 是否误将密钥或内部机密写进注释？
- [ ] 新增抽象是否减少了理解成本，还是仅为「看起来整洁」多包一层？主流程能否在入口文件内顺读？

---

## 7. 与 AI 协作

在 Cursor 等环境中，**生成代码时应默认遵守本规范**；若用户要求「少注释」或「仅英文」，以当次对话为准，但与本仓库长期维护习惯冲突时，应在回复中简短说明取舍。**禁止过度封装**：优先最小正确 diff，不为单行逻辑抽 helper，不为假想复用加中间层。
